# Scope and modelling boundaries

This repository is a **methodology and software** project about *detection*. Everything in it
is meant to be safe to publish, and these rules keep it that way.

## What is modelled

* **A synthetic system.** The navigation chain (two embedded GNSS/INS units feeding a mission
  computer over a data bus) is the generic, defense-*representative* architecture of CPS-02
  (GMCavalheri/cyber-physical-rbd-attack-trees) and CPS-01
  (GMCavalheri/cyber-attack-reliability-impact-modeling). This project adds one dissimilar
  barometric altitude source and labels it an addition. It does not describe any real
  platform, product, operator or programme.
* **Sensor behaviour** through simple, stated error models (white Gaussian noise, a constant
  accelerometer bias). Every value is an assumption, stated row by row in
  [`sensor_parameters.csv`](../src/fdicps/data/sensor_parameters.csv); the two GNSS noise
  levels are sized to the order of the public GPS SPS Performance Standard.
* **Physical faults** as the ways a unit's outputs change when its hardware degrades (step,
  drift, frozen output, more noise), with ranges in
  [`anomaly_parameters.csv`](../src/fdicps/data/anomaly_parameters.csv).
* **False data injection at the measurement level only.** An attack is the vector of values
  added to what the sensors measured before the mission computer reads them, and nothing
  else. The four sophistication levels differ only in how much *physics* that vector
  respects, which is exactly the variable the published FDI literature studies. How an
  adversary would obtain the ability to change those values, on any real bus, receiver or
  product, is **out of scope**: no vulnerabilities, procedures, tools, signal-level spoofing
  methods, protocol details or configurations appear anywhere.

## Why this is the right boundary

A detector only ever sees the values that reached it. Whether a value is wrong because a
receiver failed or because someone changed it upstream, the detection problem is defined
entirely by the measurement vector, so modelling the attack as that vector costs the analysis
nothing. The attack vectors used here (a = Hc, dynamically consistent offsets) are the
textbook constructions of the public state-estimation security literature (Liu, Ning & Reiter,
2009, and the work that followed; see [`related-work.md`](related-work.md)), published so
that defenders can build detectors against them.

## Public data only

* All training and test data are generated by this repository from seeds.
* The optional transfer test uses the public **HAI** industrial-control-system security
  dataset under its own terms. The data are downloaded by a script, never committed, and
  never redistributed.

## What is out of scope

* Real aircraft, avionics or navigation products, and any real flight data.
* Anything about gaining access to a system; offensive tooling of any kind.
* Claims about the absolute detection rates a real system would achieve. Numbers here are
  conditional on the stated models: their value is in the comparisons (which features help,
  where detection breaks down) and in the closed-form limits, not in predictive precision.
